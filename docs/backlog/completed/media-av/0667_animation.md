# 0667 — Animation: in-tree GIF/APNG decoders + the playback lane

Status: completed 2026-08-21
Owner: engine (gfx/anim, gfx/gif, gfx/apng, widgets/animated_image)
Effort: M

## The field ask

Operator, 2026-08-20, after the progressive-JPEG fix landed: "is it
possible to provide movie support as well (eg .mov, mp4, mpg, avi) or is
it starting to be too much?", with the deciding constraint stated:
permissive licences (MIT/Apache/BSD) and OS-agnostic.

## The ruling that shaped the scope

That constraint settles it, and the two halves of "movie support"
separate cleanly:

- **Decoding H.264/H.265/VP9/MPEG-1/2/4 in-tree: NO.** They are
  patent-pooled (writing our own decoder does not change that — it is
  orthogonal to source licence), and a correct real-time decoder for any
  of them is larger than this entire crate. A wrong or slow video
  decoder is worse than an honest refusal.
- **Linking `libavcodec`: NO.** ffmpeg is LGPL by default and GPL as
  commonly built (x264/x265); linking it would put an obligation
  question on every downstream user of an MIT engine.
- **Spawning `ffmpeg`: fine, but not a capability the engine claims.**
  A separate process over a pipe carries no licence obligation into this
  crate, but ffmpeg ships on no OS by default, so it cannot be what
  "supports video" means here. It is a documented pattern the CALLER
  owns.
- **Decoding what IS clean: YES.** Animated GIF (LZW patents expired
  2004) and APNG (PNG chunks over the inflate already in-tree). Both are
  permissive, patent-free, dependency-free, and identical on every OS
  with nothing installed.

A Motion JPEG demuxer for AVI/MOV shipped in the first cut and was
REMOVED before release. It decoded honestly, but MJPEG is a 2005-era
camcorder format: across the operator's own 25 video files it would have
played zero. Being able to open a `.mov` header does not make a library
a video player, and the naming it invited ("mp4 support") oversold the
result. What survives from it is the part with value: video containers
are recognized well enough to be NAMED in the refusal.

## Shipped

- `gfx::anim` — `Animation` (frames, per-frame delays, loop count),
  `Frame`, `frame_at(elapsed)`, and `decode_animation(bytes)`:
  magic-routed like `decode_image`, with a still decoding as a one-frame
  animation so one path shows any picture.
- `gfx::gif` — animated GIF87a/89a: variable-width LZW, graphic control
  extensions (delay, transparency, all three disposal modes),
  local/global palettes, interlacing, and the NETSCAPE loop count.
  Frames are composited during decode, so playback is a frame swap.
- `gfx::apng` — `acTL`/`fcTL`/`fdAT` over the still PNG decoder, with
  per-frame rects, disposal, and source-over blending. `is_animated`
  routes on a chunk-header walk; a still viewer still gets the IDAT
  image.
- `gfx::decode` — video containers (`.mp4`/`.mov`, `.avi`, `.webm`,
  `.mpg`) are recognized by magic ALONE — no demuxer, no codec table —
  and refused with the container's name plus the `ffmpeg` line that
  converts the file into an animation the engine plays.
- `widgets::AnimatedImage` — the playback lane: `.playing(signal)`,
  `.repeat(bool)`, the same fit/align/mosaic-family surface as `Image`,
  and the labeled broken state carrying the decoder's message.
- `decode_image` and `probe_dimensions` learned GIF (first frame /
  logical screen descriptor), so markdown image blocks and
  `Image::from_path` take a `.gif` without knowing about animation.
- `examples/movie.rs`, and the external-decoder pattern documented in
  `docs/graphics-and-3d.md` § "Moving pictures".

## The cost, stated

Playback arms ONE timer per frame for that frame's own delay: a paused
or finished clip arms nothing, a still arms nothing, and nothing wakes
between frames — the zero-idle law survives with one honest exception
while a picture is actually moving. Mosaic repaints are a cell diff, so
motion is cheapest on the universal channel and most expensive on the
pixel protocols, which re-send a full payload per frame.

## Evidence

- Fixtures are a 3-frame clip written by a real encoder (Pillow),
  regenerated byte-for-byte by `tools/make_anim_fixtures.py`: GIF, APNG,
  and a structurally valid H.264 `.mp4` whose only job is to be refused.
- GIF and APNG are pinned against the generator formula EXACTLY
  (lossless formats, so no tolerance).
- Truncation ladders and byte-soup fuzz on both decoders; the refusal
  path is pinned to name the container AND carry the `ffmpeg` line,
  through both `decode_animation` and `decode_image`.
- Playback is pinned through the engine's own timer wheel: one timer per
  frame, frames advance in order, and a finished clip leaves nothing
  armed.
- Real-world check: all 25 video files in the operator's own
  Pictures/Movies/Downloads are H.264 — every one refuses by name, and
  none would have played under any in-tree decoder we were willing to
  write.

## What this is NOT

Video support. The engine decodes no video codecs, and the docs say so
in those words. "Plays animated GIFs" is the claim; anything more would
have to come from an external decoder the CALLER owns (the ffmpeg
subprocess pattern in `docs/graphics-and-3d.md`), which is a separate
item if a consumer ever needs it.

## What remains open

`0665` (kitty `a=f`/`a=a` animation lane) is untouched and still worth
doing for LOOPING content: on kitty the terminal can animate autonomously
at zero steady-state bytes. It does not help streaming video, where
every frame is new data on every channel.
